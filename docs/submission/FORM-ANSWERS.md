## Domain / goal

My domain is cyber security incident investigation, and my goal was to build an autonomous agent that investigates suspicious login activity end to end. The agent takes a goal in plain English, reads the login logs, checks the IP and device history, links every fact into an evidence graph, checks its own verdict against that graph, and only then writes an incident report with a risk level and a recommendation. Three rules shaped the whole design. First, no decision from a single alert: a verdict has to be backed by several edges in the graph. Second, no guessing on thin evidence: when the score sits between the thresholds, the agent says INSUFFICIENT_EVIDENCE and lists exactly what is missing, instead of making a confident call. Third, no dangerous action without a human: the agent never blocks an IP or resets a password on its own, and every run ends with approval status PENDING. I built it for the Xiarch Bharat Agentic AI Engineer Intern assessment, and I tested it on 20 hand-designed synthetic traces, 12 malicious and 8 benign, because I wanted numbers I could defend instead of claims I could not back up.

## Write-up — design decisions

I made five design decisions, and each one is real code, not a diagram. First, the Evidence Graph in `sentinel_x/graph.py`, built on NetworkX: every fact (IP, user, device, login attempts, time, country) becomes a node or an edge, and each edge carries a `supports` label of malicious, benign, or neutral. Second, the Dynamic Investigation Planner in `sentinel_x/planner.py` and `sentinel_x/agent.py`, built on a LangGraph `StateGraph` with ten nodes and a conditional branch: in live mode the LLM picks the next tool from the evidence so far, and in offline mode the same five step names run in a fixed order so the pipeline can be tested without a key. Third, the Self-Verification Engine in `sentinel_x/verifier.py`: after a draft verdict, it re-checks the verdict against the graph, and a MALICIOUS verdict needs at least 3 malicious-supporting edges or it is revised to INSUFFICIENT_EVIDENCE. Fourth, Uncertainty and Abstention in `sentinel_x/uncertainty.py`: score 3.0 or more means MALICIOUS, 1.0 or less means BENIGN, and anything between means INSUFFICIENT_EVIDENCE. Fifth, the Explainable Audit Trail in `sentinel_x/audit.py`: every tool call, decision, revision, and recommendation goes into SQLite (`sentinel_x.db`) and a JSON trace per run, so any verdict can be replayed step by step.

## Write-up — limitations

I want to be plain about what this is not. The live Gemini run is pending a free API key, so every number in this submission comes from an offline evidence-graph evaluation, not from a live LLM run. The LLM did not reason in those 20 runs; the transparent scorer in `sentinel_x/graph.py` stood in for it, and the live LLM path in `planner.py`, `llm.py`, and `agent.py` has not been measured yet. Second, the test data is synthetic: 20 hand-designed traces with TEST-NET documentation IPs (192.0.2.x, 198.51.100.x, 203.0.113.x), no real attacks and no real users, so the metrics describe those 20 traces and nothing more. Third, the agent never takes a dangerous action on its own, by design, which means it is a reporting and recommendation tool, not an automated response tool. Fourth, the IP lookup skips real lookups for TEST-NET IPs, and the threat-intel search uses the free DuckDuckGo HTML page, which can change shape or fail and then returns zero hits. Fifth, the React frontend falls back to bundled sample data when the FastAPI backend is not running, so the dashboard shows demo numbers unless the backend is up. None of these limits is hidden anywhere in the repo.

## Assumptions / mock data

All data in this project is mock and synthetic, and I designed it that way on purpose so no real person or system is involved. Every IP is an RFC 5737 TEST-NET documentation range: 192.0.2.x, 198.51.100.x, or 203.0.113.x. The user in every trace is the synthetic name `unknown-user`, and there are no real names, no real email addresses, and no real log files anywhere in the repo. The 20 test traces live in `data/synthetic_traces.csv` and `data/synthetic_traces.json`, and I hand-designed each one: 12 malicious traces combine several suspicious signals at once (many failed logins at night, an unknown device, a country change, then a success after the failures), and 8 benign traces have few failures in the daytime from a known device with no country change. Two traces sit between the scoring thresholds on purpose, SX012 and SX020, so I could check that the agent abstains instead of guessing. I also assume the offline scoring bands in `sentinel_x/uncertainty.py` (3.0 and 1.0) are reasonable for this small synthetic set, and I do not claim they would hold on real logs without re-tuning. The demo goal (IP 192.0.2.45, 35 failed logins, 1 success, 02:30 AM, unknown device) is the same kind of hand-written synthetic input, trace SX-DBB1B7B7.

## Write-up — approach

I built SENTINEL-X step by step, in an order I could test at each stage, instead of writing everything at once and debugging it all at the end. I started with the LLM layer in `sentinel_x/llm.py`: a Gemini REST client with Groq and OpenAI fallbacks, and JSON parsing with retries because the model kept wrapping answers in markdown fences. Then I built the evidence graph in `sentinel_x/graph.py`, then the tools in `sentinel_x/tools.py` (log analysis with pandas, IP lookup, threat-intel search), then the LangGraph planner and agent in `sentinel_x/planner.py` and `sentinel_x/agent.py`, then verification in `sentinel_x/verifier.py`, abstention in `sentinel_x/uncertainty.py`, and audit logging in `sentinel_x/audit.py`. After the pipeline ran, I added the Streamlit dashboard in `app.py`, the 14 tests in `tests/test_sentinel_x.py`, and the evaluation in `evaluation/run_evaluation.py`. I ran the demo in offline mode (trace SX-DBB1B7B7, verdict MALICIOUS, score 5.0, 4 tool calls, 0.743 seconds), ran the full test suite until all 14 passed, and ran the evaluation over the 20 synthetic traces to get the numbers below. Nothing in the reports is invented: every metric comes from `evaluation/evaluation_report.json`, and the per-trace table in the monitoring report lists all 20 traces with their scores, predictions, tool calls, and times.

## Precision / recall

These numbers are from the offline evidence-graph evaluation over 20 synthetic traces (12 malicious, 8 benign), computed with scikit-learn by `evaluation/run_evaluation.py` and stored in `evaluation/evaluation_report.json`. The LLM was not exercised; a live Gemini run is pending a free key. Precision is 1.0: every trace the agent called MALICIOUS was truly malicious, with 11 true positives and 0 false positives. Recall is 0.9167: it caught 11 of the 12 truly malicious traces, and the one it missed is SX012, a deliberately borderline trace (score 2.0) where the agent abstained with INSUFFICIENT_EVIDENCE instead of guessing — that abstention is the feature working as designed, and it is counted as a false negative, not hidden. F1 score is 0.9565. False positive rate is 0.0: none of the 8 benign traces was called malicious, with 8 true negatives. Investigation completion rate is 0.90: 18 of 20 traces got a firm verdict and 2 abstained (SX012, malicious, score 2.0; and SX020, benign, score 1.5). Average tool calls per investigation is 4.0, average execution time is 0.839 seconds, and the unsupported conclusion rate is 0.0, meaning 0 of 20 conclusions had no supporting graph edge. Abstentions count as NOT malicious for precision and recall, which is the honest way to score them.

## Production-readiness

SENTINEL-X is not production-ready yet, and I would not claim it is. What is ready: the full pipeline runs end to end, all five features are real code, 14 tests pass, every run is audit-logged in SQLite and JSON, and the human-approval gate means no dangerous action can happen by accident. What is still needed before production is four things. First, a live Gemini run with a free API key on the same 20 traces, and then on real anonymised logs, to measure how the LLM actually reasons — the offline numbers only describe the evidence-graph scorer, not the LLM. Second, a real threat-intel API key instead of the free DuckDuckGo HTML search, which is fragile and returns no detail. Third, a proper human-approval interface with roles and access control, so approving a block is a real action with a named approver and a timestamp, not a line in a report. Fourth, testing on more, larger, and messier data: traces with missing fields, out-of-order events, several IPs in one incident, and logs from real systems, to see where the abstention rate and the false positive rate actually land. Until those four are done, the honest statement is that this is a working prototype with measured offline results, a clear audit trail, and a safe default of asking a human before it acts.

## How test traces were generated / labelled

The test traces were generated by me, by hand, as synthetic data — no real data was used anywhere. I wrote 20 traces into `data/synthetic_traces.csv` and `data/synthetic_traces.json`, each with an id (SX001 to SX020), a label (malicious or benign), an IP, a failed-login count, a successful-login count, an hour, a device_known flag, and a country_change flag. I labelled each trace when I wrote it, from the signals I put into it, not after running the agent: a trace is malicious when I designed it with several suspicious signals together, such as 35 failed logins at 02:00 from an unknown device with a country change and then a success, and benign when I designed it with few failures in the daytime from a known device with no country change. Two traces are deliberately borderline so the abstention logic gets tested: SX012 (9 failures, 0 successes, 2 am, known device, no country change, score 2.0, labelled malicious) and SX020 (6 failures, 1 success, 1 am, known device, no country change, score 1.5, labelled benign). Both abstained, which is what they were built to check. All 20 IPs are TEST-NET documentation ranges (192.0.2.x, 198.51.100.x, 203.0.113.x), so nothing points to a real person or system, and the same 20 labelled traces are shipped as `docs/submission/03-Synthetic-Test-Traces.csv` and `.json` for the submission.
